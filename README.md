# my-graph-agent — 노란봉투법 입법 과정 지식그래프 에이전트

실습 과제("지식 그래프 에이전트 만들기")로, 22대 국회의 노란봉투법(노동조합 및 노동관계조정법 개정) 입법
과정을 도메인으로 삼아 여러 문서에 흩어진 정보를 그래프로 엮고, 멀티홉 검색으로 근거·경로를 함께 제시하는
챗봇을 만든다. 

## 사용한 외부 데이터 출처 (참고용 요약)

| 출처 | 용도 | 실제 사용한 서비스ID / 경로 |
|---|---|---|

| [국회도서관 발언 빅데이터](https://dataset.nanet.go.kr) | 회의록 발언 전문 검색·수집 | 홈 검색창(`srchQ`) → 결과 카드(`selectMeetingDetail(conferNum)`) 클릭 → 발언 목록. 정식 "데이터셋 다운로드"(전체 발언 export) 기능도 있으나 자동화는 미완성 — 아래 "알려진 한계" 참고 |
| [의안정보시스템](https://likms.assembly.go.kr) | 의안번호·발의자·처리결과 1차 확인(수동) | `data/seed_bills.json`의 근거 |
| 웹 검색 | 정부위원(장관·차관) 프로필, 동명이인 확인 | `data/docs/people/*.md` 중 정부위원 4명 |

`data.go.kr`(공공데이터포털) 키는 시도했으나 불필요했다(권한 없는 서비스였음). API 탐색 경위는
`data/RESEARCH_NOTES.md`, 각 스크립트 상단 주석 참고.

## 진행 상황 — 5단계 전부 완료 (2026-09-21 기준)

| 단계 | 상태 | 비고 |
|---|---|---|
| 1. 자료 수집 · 골든셋 | ✅ 완료 | 문서 51건(법안 19 + 회의록 5 + 인물 프로필 27), 골든셋 13문항(`data/goldenset.json`) |
| 2. 그래프 구축 (`build_graph.py`) | ✅ 완료 | 노드 44(법안19·인물22·위원회3), 엣지 66(발의23·심사22·입장표명21) |
| 3. 멀티홉 검색·답변 (`agent.py`) | ✅ 완료 | LangGraph 파이프라인, 골든셋 6문항 수동 검증 전부 통과 |
| 4. 평가 (`evaluate.py`) | ✅ 완료 | 그래프 9/13(수동 확인 시 10/13) vs basic RAG 1/13 |
| 5. 웹 데모 (`app.py`) | ✅ 완료 | streamlit, 로컬 실행 확인 (스크린샷: `docs/screenshots/`) |

과제 제출물인 **[`REPORT.md`](REPORT.md)**에 주제·코퍼스, 골든셋·스키마, 파이프라인 아키텍처
다이어그램, 측정 결과와 실제로 겪은 실패 사례 7건, 데모 설계, 회고를 정리해 뒀다. 아래는 개발
진행 로그이고, 제출용 요약은 REPORT.md를 보면 된다.

### 주제를 고른 이유

여야 입장차가 뚜렷하고, 여러 의원이 발의한 유사 법안이 병합심사되어 개체가 자연스럽게 겹치며, 정부
입장이 정권 교체를 기점으로 뒤집힌 것까지 회의록에 남아 있어 골든셋 소재로 적합했다. 상세 배경·타임라인은
[`data/RESEARCH_NOTES.md`](data/RESEARCH_NOTES.md) 참고.

### 그래프 구축 (`build_graph.py`)

- **PROPOSED_BY/REVIEWED_BY는 LLM 없이 결정론적으로 추출**: `seed_bills.json`의 의안명 문자열에
  발의자명이 이미 구조화돼 있고("...(박해철의원 등 14인)"), 심사 위원회도 API로 확인된 사실이라
  텍스트 정규식 파싱만으로 충분했다.
- **STATED_POSITION_ON만 회의록에서 LLM(gpt-4o-mini)으로 추출** — 5개 회의당 1회 호출(발언자별
  개별 호출 X)로 그 회의의 등록된 발언자 전원을 한 번에 찬성/반대/조건부/설명/해당없음으로 분류.
  결과가 정당별 성향과 실제로 일치함을 확인함(국민의힘 위원 반대·조건부 다수, 여당 위원 찬성 다수).
- **정규화**: "위원장 안호영", "OOO 위원" 같은 직함을 떼고 순수 이름만 남김. 위원장 대안의
  제안자로 찍히는 "환경노동위원장"(직함)은 실제 재임자 안호영으로 별칭 병합.
- **발견한 버그와 수정**: `053920.md`는 96%가 무관한 환경부장관 후보자 인사청문회이고 노동조합법
  상정은 맨 끝 4%뿐이었다. 발언자별 앞부분만 잘라 보냈더니 위원들의 청문회 발언(후보자 검증)이
  노동조합법 반대 의견으로 오분류되는 버그가 발생 → 해당 파일만 상정 시점 이후로 잘라서 해결.
  부수적으로, 회의록 파싱 단계에서 "발언자" 목록 누락으로 위원장 발언에 병합됐던 이정식 장관의
  발언도 LLM이 문맥으로 스스로 재분리해 정확히 잡아냄.
- 산출물: `output/graph.graphml`(그래프), `output/build_log.json`(모든 STATED_POSITION_ON 판단 근거,
  감사용).

### 멀티홉 검색·답변 (`agent.py`)

LangGraph 파이프라인: `find_entities`(질문에서 그래프 노드명을 문자열로 직접 매칭, LLM 불필요) →
`expand_hop`(최대 3홉, 조건부 엣지로 반복) → `generate_answer`(수집된 근거만으로 LLM이 답변 작성,
경로는 LLM이 아니라 상태에서 그대로 뽑아 프로그램이 직접 구성 — 경로를 지어낼 여지를 없앰).

- **허브 회피**: 차수 6 초과 노드(환경노동위원회·2211924·2202444)를 허브로 보고, 이웃을 전부
  펼치지 않는다. 1차로 질문의 관계 키워드("제안/발의"→PROPOSED_BY, "심사/위원회"→REVIEWED_BY,
  "입장/찬성/반대"→STATED_POSITION_ON)로 걸러내되, 그 노드가 해당 관계를 아예 안 가지면(예:
  환경노동위원회는 REVIEWED_BY만 있음) 필터를 무시하고 원래 후보로 되돌린다. 그래도 남으면
  질문과의 키워드 겹침 점수로 상위 6개만 남긴다. 질문에 직접 언급된 노드는 점수와 무관하게 항상 포함.
- **찾은 버그와 수정**: 위원회 허브를 지날 때 "같은 위원회를 공유한다"는 사실만으로는 "병합됐다"를
  증명 못 한다는 게 실제로 드러났다 — `decision_result`가 그냥 "대안반영폐기"라고만 돼 있어서 에이전트가
  어느 대안으로 흡수됐는지 근거로 못 찾고 "확인되지 않습니다"라고 잘못 답했다. `build_graph.py`에서
  라운드별 위원장 대안 번호를 `decision_result`에 명시적으로 채워 넣는 정규화를 추가해서 해결함
  (`대안반영폐기` → `대안반영폐기(2202444)`). 그래프 구조만으로는 부족하고 속성 정규화가 꼭 필요했던
  사례라 REPORT.md 실패 분석에 넣을 만하다.
- **골든셋 6문항 수동 검증**: 단순-01(제안자), 멀티홉-01(대안 흡수), 단순-03(김영훈 입장),
  멀티홉-05(반대 근거 없음 → 정확히 거절), 전역-02(이수진 3건 집계) 등 전부 기대 정답과 일치.

### 평가 (`evaluate.py`)

골든셋 13문항을 그래프 에이전트와 basic RAG(그래프 없이 키워드 겹침 상위 문서 5개만 주고 답하게 한
것)로 각각 풀게 하고 LLM 판정관(gpt-4o-mini)으로 채점. 결과: `output/eval.json`.

| 홉 | 그래프 | basic RAG | 경로 재현율 |
|---|---|---|---|
| 1홉 | 5/6 | 0/6 | 100% |
| 2홉 | 2/3 | 1/3 | 90% |
| 3홉 | 0/1 | 0/1 | 100% |
| 전역 | 2/3 | 0/3 | N/A |
| **전체** | **9/13** | **1/13** | |

(evaluate.py를 연달아 돌리면 개체 링킹 LLM 폴백의 비결정성 때문에 8~9/13 사이로 ±1 흔들린다 —
아래 "평가 자체의 변동성" 참고.)

- **그래프가 basic RAG를 확실히 앞선다** — 특히 1홉(관계 하나만 타면 되는) 질문에서 basic RAG는
  0/6인데 그래프는 5/6. 키워드 겹침만으로는 "누가 제안했는가" 같은 관계형 질문에 원천적으로 약하다.
- **1차 평가에서 찾은 버그 2개를 실제로 고치고 재평가함** (6/13 → 9/13):
  1. **엣지 기록 버그**: 같은 홉에서 두 시작 개체가 서로 다른 관계로 같은 노드를 가리킬 때(예:
     환경노동위원회는 REVIEWED_BY로, 김영훈은 STATED_POSITION_ON으로 같은 법안 2211924를 가리킴),
     먼저 처리된 쪽이 그 노드를 방문 처리해 버려서 뒤에 오는 진짜 필요한 엣지가 통째로 사라졌다.
     "방문 처리(재확장 방지)"와 "엣지 기록"을 분리해서 해결.
  2. **개체명이 없는 질문("동일 인물인가?" 등)은 시작점을 못 찾던 문제**: 문자열 매칭 대신 LLM에게
     "이 질문은 그래프의 어느 노드에서 시작해야 하나"를 물어보는 폴백을 추가. 또한 "위원장이
     누구였나"를 그래프 관계로는 알 방법이 없던 문제는, 관계를 늘리지 않고 위원회 노드에
     `chair_2024`/`chair_2025`/`subcommittee_chair_2024` 같은 속성 한 줄씩만 추가해서 해결
     (`build_graph.py`의 `extract_chairs`) — 위원장의 절차 발언 자체는 여전히 관계로 안 뽑는다.
- **남은 실패는 전부(4/4) 생성 단계** — 색인·탐색 실패는 이번 세션에서 다 해결했다.
  허브 통과 시 남기는 후보 수(MAX_HUB_FANOUT)를 6→10으로 늘리고, 한국어 조사가 단어에 붙는
  문제("계류**로**"가 "계류"와 매칭이 안 되던 것)를 간단한 접미사 제거로 보완한 뒤에는,
  멀티홉-04(계류법안 4건 이유)도 필요한 근거가 그래프에서 다 잡히는 걸 확인했다 — 그런데도
  최종 답변은 여전히 "확인되지 않습니다"로 나왔다. 즉 **문제가 탐색에서 생성으로 완전히 옮겨감**.
  - **생성 3건**(멀티홉-02, 멀티홉-04, 전역-01): 특히 멀티홉-02·04는 근거를 직접 확인해 보니
    필요한 사실(법안들의 decision_result와 발의자)이 전부 정확히 모여 있었는데도 LLM이 여러 줄을
    엮어서 결론 내는 걸 실패하고 "확인되지 않습니다"로 도망쳤다. 답변 프롬프트를 구체화해봤지만
    (decision_result를 하나씩 대조하라고 명시) 안 고쳐졌다 — gpt-4o-mini가 흩어진 근거 여러 줄을
    종합하는 데 약하다는 실제 한계로 보고, 더 큰 모델을 쓰거나 근거를 사전에 구조화해서 주는
    방법이 다음 개선 방향이다.
  - **판정관 오류 1건**: 전역-02(이수진 3건 집계)는 답변이 실제로는 정답인데(2202259 계류,
    2211108·2211111 대안반영폐기) LLM 판정관이 "법안 제목·발의일이 정답과 다르다"며 오답
    처리했다. 판정 프롬프트에 "의안번호 대신 다른 방식으로 식별해도 같은 법안이면 정답으로
    인정하라"는 규칙을 추가했는데도 이 문항에서는 안 고쳐졌다 — 수동으로 원문 대조해서 확인함.
    LLM 판정관도 완벽하지 않다는 것 자체가 유의미한 발견이라 수동 보정 없이 그대로 기록해 두고,
    실질 정답률은 10/13으로 본다.
  - **평가 자체의 변동성**: 개체 링킹 LLM 폴백의 비결정성 때문에 evaluate.py를 연달아 두 번
    돌리면 8/13과 9/13처럼 ±1 정도 차이가 난다(전역-03이 한 번은 색인 실패, 한 번은 성공).
    "LLM 기반 평가는 한 번 돌린 숫자를 그대로 믿으면 안 되고 여러 번 돌려서 범위로 봐야 한다"는
    것도 이번에 직접 확인한 사실이라 남겨 둔다.
- **basic RAG의 약점**: 긴 회의록(예: 053920.md, 17만자)을 앞 1500자만 잘라서 컨텍스트로 주다 보니,
  정작 필요한 내용이 문서 뒷부분에 있으면(실제로 그랬다) 통째로 놓친다. 그래프는 정확한 노드/엣지
  단위로 근거를 찾아가므로 이 문제가 없다 — 멀티홉·구조화된 사실 질문에서 그래프가 유리한 이유.
- **찾은 또 다른 특성**: 개체 링킹 LLM 폴백이 temperature=0인데도 100% 결정적이지 않아서(직접
  같은 질문을 5번 돌려서 확인, 약 4번에 1번꼴로 빈 리스트 반환) 재시도 3회를 넣었다 — LLM 기반
  단계는 재시도 로직 없이는 신뢰하기 어렵다는 걸 실제로 겪은 사례.

### 웹 데모 (`app.py`)

streamlit 한 페이지: 질문 입력 → 답변·탄 경로·근거를 보여준다. 사이드바에서 골든셋 질문을
클릭 한 번으로 채울 수 있고, 체크박스로 basic RAG 답변과 나란히 비교해 볼 수 있다.

- **경로/그래프 시각화는 plotly 같은 라이브러리 없이 텍스트 목록으로 처리했다** — 노드 44개
  규모에서는 그림보다 "A —관계→ B (n홉)" 목록이 오히려 더 빨리 읽힌다. (이 결정은 대화 중
  "그때 가서 정하자"고 미뤄뒀던 것을 이 단계에서 실제로 정한 것이다.)
- 근거 원문은 기본적으로 접어 두고 펼쳐서 보게 했다(양이 많아서 — 개당 최대 100건 가까이 나옴).
- **실제로 로컬에서 띄워서 확인함**: `streamlit run app.py`로 서버를 띄우고 Playwright로 직접
  질문을 클릭·입력해서 답변·경로·근거·basic RAG 비교가 다 정상 렌더링되는 걸 확인했다.
  스크린샷: [`docs/screenshots/app_answer.png`](docs/screenshots/app_answer.png)(답변+경로),
  [`docs/screenshots/app_evidence.png`](docs/screenshots/app_evidence.png)(근거 펼친 화면).

**실행 방법**: `streamlit run app.py` (사전에 `python build_graph.py`로 `output/graph.graphml`이
있어야 함). 브라우저가 자동으로 열리고, 로컬 주소(기본 http://localhost:8501)로 접속된다.

### 아직 할 일

과제 자체는 5단계 전부 완료. 남은 건 `REPORT.md` 작성 (주제·코퍼스, 골든셋·스키마, 측정 결과,
파이프라인 아키텍처 다이어그램, 데모 설계, 회고).

## 실행 방법 (현재까지 있는 것만)

```bash
pip install -r requirements.txt
cp .env.example .env   # ASSEMBLY_API_KEY 채우기 (열린국회정보에서 발급)

python scripts/fetch_bills.py              # data/docs/bills/*.md 생성
python scripts/fetch_committee_reviews.py  # data/committee_reviews.json 생성
python -m playwright install chromium      # fetch_speeches.py 최초 실행 전 1회
python scripts/fetch_speeches.py           # data/docs/meetings/*.md 생성
python scripts/fetch_member_profiles.py    # data/docs/people/*.md 생성 (국회의원 23명)
python build_graph.py                      # output/graph.graphml, output/build_log.json 생성
python agent.py "질문"                      # 단발 질의 (경로·근거 확인용)
python evaluate.py                          # output/eval.json 생성 (골든셋 채점 + basic RAG 대조)
streamlit run app.py                        # 웹 데모 실행 (http://localhost:8501)
```

## 알려진 한계

- `record.assembly.go.kr`(국회 회의록시스템)의 검색 폼은 자동화에 실패했다 — 검색 버튼이 JS
  아코디언 뒤에 있고 실제 제출 로직을 특정하지 못했다. 대신 국회도서관 발언 빅데이터
  (dataset.nanet.go.kr)로 회의록 발언 수집에 성공했으니 이쪽은 참고만 하면 된다
  (상세: `scripts/fetch_committee_reviews.py` 상단 주석).
- `scripts/fetch_speeches.py`는 검색 결과 화면에 렌더링된 발언만 가져온다(스크롤해도 추가 로드 안
  됨). **이건 사이트 자체의 한계가 아니라 우리 수집 방식의 한계다** — 국회도서관 사이트에는 정식
  "데이터셋 다운로드" 기능이 있고 "검색된 안건 내의 모든 발언 포함" 옵션으로 전체를 받을 수 있는
  걸 확인했는데, 이 다운로드 모달 자동화(Playwright)에는 성공하지 못했다(같은 체크박스 id를 가진
  안 보이는 모달 사본이 여러 개 있어서 자동화 도구가 진짜 보이는 요소를 못 찾음). 코퍼스를 더
  키운다면 화면 스크래핑 대신 이 다운로드 기능을 자동화하는 게 우선순위다. 또한 아주 드물게 발언이
  1회뿐인 화자(예: 다중 안건 회의에서 잠깐 등장한 인사)가 "발언자" 필터 목록에서 빠져 직전 화자
  블록에 병합되기도 한다(예: `053920.md`의 이정식 장관 발언 — 원문은 `data/RESEARCH_NOTES.md`에
  직접 인용해 둠).
- 열린국회정보 API 서비스ID는 문서마다 다르게 적혀 있어 혼동하기 쉽다. 이 프로젝트에서 실제로
  동작을 확인한 것은 `TVBPMBILL11`(의안검색), `BILLINFODETAIL`(처리경과), `BPMBILLSUMMARY`(제안이유),
  `TVBPMCONFINFO`(소위 심사정보), `nwvrqwxyaytdsfvhu`(국회의원 인적사항) 5개뿐이다. `data.go.kr` 키는
  필요 없다.
- `nwvrqwxyaytdsfvhu`(국회의원 인적사항)는 국회의원 DB라 장관·차관은 안 나오고, 이름이 흔하면
  동명이인이 걸릴 수 있다 (예: "김민석"으로 검색하면 2024년 고용부차관이 아니라 국무총리 김민석이
  나옴). 결과의 정당·위원회가 맥락과 맞는지 반드시 확인할 것.
